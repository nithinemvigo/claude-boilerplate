How a task runs — /start

Universal entry point for any change: feature, bug fix, hotfix, refactor, chore, docs. The classifier sizes the task; the orchestrator routes it to the right pipeline; each stage stops at its gate for your approval.

<task_size>
standard</task_size>
<branch>feature/stripe-billing-checkout</branch>
<reason>Touches 4 files; no contract change; contained to checkout layer.</reason>
# → orchestrator loads pipeline-standard.md, CEO agent activates...

Three tiers — the classifier picks one

Sizing is automatic. The classifier (~50 tokens) runs before anything else loads, then the orchestrator routes to the matching pipeline.

The eight stage agents

Each agent is one file in .claude/agents/. The orchestrator activates them in the order the pipeline requires; gates between stages enforce explicit approval before the next agent starts.

🔢

classifier .claude/agents/classifier.md

Runs first on every /start. Reads the description, emits <task_size> (nano / standard / full) and <branch> (feature/, bugfix/, or hotfix/). ~50 tokens.

🏛️

ceo .claude/agents/ceo.md

Task intake, flow routing, brief production. Outputs flow_type tag — backend-feature, frontend-feature, hotfix, design-only, or security-patch. Gate: /plan-ceo-review.

🛠️

eng .claude/agents/eng.md

Technical spec. Writes docs/spec-<id>.md. Resolves data model, API contracts, service boundaries. Gate: /plan-eng-review.

🎨

design .claude/agents/design.md

UI spec + design tokens. Only activates when the flow includes Design (frontend-feature, design-only). Writes docs/design-<id>.md.

⚒️

build .claude/agents/build.md

Implementation. Writes code, updates docs/progress.md. If scope grows mid-task, emits <escalate> and the orchestrator re-classifies into a bigger tier.

🧪

testing .claude/agents/testing.md

Test suite + security validation. Loops back to Build on failures. Required for standard and full tiers.

🔍

review .claude/agents/review.md

The commit gate. Only stage permitted to issue git commit. The orchestrator rejects git commands from any other stage. Loops back to Build on any blocker finding.

🚢

ship .claude/agents/ship.md

Merge, tag, retrospective. Runs only after Review approval and Reviewed-by: review-agent appears in the commit. Writes the retrospective and updates the changelog.

Escalation: if Build discovers mid-task that the scope is bigger than the classifier estimated, it emits <escalate>standard|full</escalate>. The orchestrator pauses, re-classifies, reloads the bigger pipeline, and resumes from Build — work on the branch is preserved.

Step-by-step walkthrough — a standard task, end to end

Concrete trace of what happens after you run /start add rate limiting to the API. Most projects spend most of their time in this tier.

1

You type /start add rate limiting to the API

The classifier loads first (~50 tokens). Nothing else runs until it emits its tags.

<task_size>standard</task_size>
<branch>feature/api-rate-limiting</branch>
<reason>3 files (middleware + route + tests), no contract change, contained to API layer.</reason>
2

Orchestrator activates

Reads the classifier's tags. Loads .claude/workflows/pipeline-standard.md. Creates the branch feature/api-rate-limiting. Activates the CEO agent next.

3

CEO (lean) — task brief

Produces a short brief: scope, success criteria, affected modules. Writes docs/brief-<id>.md. Skips the heavy /office-hours + /plan-ceo-review calls that the full tier uses. Gate: you run /approve to advance to Build.

4

Build — implementation

Implements the change on the branch. Writes the middleware module, wires it into the route, adds tests. Updates docs/progress.md as it goes. If scope balloons (turns out you need a new Redis dep, or it touches auth too), Build emits <escalate>full</escalate> and the orchestrator re-classifies. Gate: code-review plugin runs a self-check; clean before advancing.

5

Review — the commit gate

Reads the brief, the implementation, and the test results. Calls code-review and security-guidance plugins on the staged diff. Emits one of VERDICT: Approve, Request Changes, or Needs Discussion.

On Approve: Review issues git commit with Reviewed-by: review-agent in the message. This is the only stage permitted to commit. The orchestrator rejects git commands from any other stage. On Request Changes, loops back to Build with the findings.

6

Ship (lean) — merge & tag

Verifies the Reviewed-by: review-agent tag is present in the commit. Pushes the branch, opens the PR, tags the release. Updates CHANGELOG.md. Writes a one-line retrospective entry.

Done. Branch is open, PR is up, tag is set. The full task touched ~1500 tokens of orchestration plus whatever the implementation needed.

The pre-commit pipeline

Every git commit in applied projects triggers 4 gates — the commit is rejected if any fail.

1

ESLint

Checks for syntax and lint errors. Blocks the commit and prints the exact errors. Run npm run lint:fix to auto-fix.

2

Prettier Check

Ensures consistent code formatting. Run npm run format to auto-fix any formatting drift.

3

🛡️ Security Review /security-review plugin

Scans the staged diff for injections, XSS, hardcoded secrets, path traversal, and SSRF. Blocks on any finding.

4

🔍 Code Review /code-review plugin

Runs a focused code review on the diff using your ensemble of security, performance, a11y, and docs agents. Blocks if verdict is "Request Changes".
