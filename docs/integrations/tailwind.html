Rule file highlights (tailwind.md)

  • Class order matters for readability. Use prettier-plugin-tailwindcss to auto-sort. The pre-commit Prettier check enforces this.
  • Extend the theme, don't override. theme: { extend: { colors: {...} } } keeps Tailwind's defaults; overriding loses them.
  • Avoid arbitrary values. h-[37px] is a code smell — add the value to the theme if it appears more than twice.
  • Don't @apply reflexively. If you find yourself wrapping utilities in custom classes, the right answer is usually a component, not a class.
  • Responsive prefixes go in mobile-first order: w-full md:w-1/2 lg:w-1/3.
  • Dark mode: use class strategy (not media) so users can toggle.
  • Don't fight the UI/UX Pro Max skill. The ui-ux-pro-max skill in core/ ships 96 palettes and 57 font pairings — check it before inventing your own.

Combined with other integrations

  • + supabase on nextjs-ts — common SaaS shape, server-rendered UI with auth-gated data.
  • + firebase on react-vite-ts — covered by the firebase-react preset.
  • + prisma on nextjs-ts — half of T3 stack.

Gotchas

  • Tailwind v4 vs v3. v4 ships with a new config style (CSS-first). The rule file targets v4 by default but flags both.
  • JIT scanning. If your content paths are wrong in tailwind.config.js, classes silently won't generate. Verify by checking the output CSS in dev.
  • Plugin order. If using @tailwindcss/forms + @tailwindcss/typography, register both before your own plugins.
  • PurgeCSS isn't needed — Tailwind's JIT engine handles unused-class removal.
