prisma

Type-safe ORM with declarative schema and migrations. The integration adds team conventions for schema design, migration discipline, and where Prisma can and can't go in a Next.js app.

ORMbackendmigrationstyped

Environment variables

# Primary connection — used by the app at runtime
DATABASE_URL="postgresql://user:pass@host:5432/db?schema=public"

# Direct connection — bypasses connection poolers (PgBouncer, Supavisor) for migrations
# Required when using Supabase, Neon, PlanetScale, or any pooled database
DIRECT_URL="postgresql://user:pass@host:5432/db?schema=public"

Rule file highlights (prisma.md)

  • Schema is the source of truth. Don't ALTER TABLE by hand — change the schema, run prisma migrate dev.
  • Never edit applied migrations. Add a new migration to fix something. Migrations are append-only.
  • Singleton PrismaClient. One instance per process. In Next.js dev, attach it to globalThis to survive HMR.
  • Always select fields explicitly. findMany({ select: { id: true, name: true } }) beats findMany() for both perf and security.
  • Transactions for multi-step writes. Use $transaction([...]) or interactive transactions; never expect "it'll be fine" on cross-row writes.
  • Raw SQL only when necessary. $queryRaw + tagged templates for parameter binding — string concatenation in raw SQL is a SQLi waiting to happen.
  • Connection pooling. Use DIRECT_URL for migrations and DATABASE_URL via the pooler for runtime. Supabase, Neon, and PlanetScale all require this split.
  • Don't import Prisma in Client Components. The Next.js compiler will fail; the rule reinforces this.

Combined with other integrations

  • + supabase — use Prisma against Supabase's Postgres. Supabase Auth still works alongside Prisma queries. RLS still applies — Prisma queries run as the database user, not the authenticated user, so put your auth logic at the application layer.
  • + tailwind on nextjs-ts — half of T3 stack.
  • + trpc (v2) — common pairing: Prisma queries inside tRPC procedures, type-safe end-to-end.

Gotchas

  • Schema location. prisma/schema.prisma is the convention. Don't move it without updating CI scripts.
  • Generated client. npx prisma generate writes to node_modules/.prisma/client. Add it to your build step — the client is type-checked against your schema.
  • Edge runtime limitations. Prisma doesn't work in the Edge runtime out of the box. Use the Data Proxy (prisma://) or Accelerate, or run on the Node runtime.
  • Seeding. Add a prisma/seed.ts and register it in package.json's "prisma": { "seed": "..." }.
  • Migration drift. If someone runs prisma db push in prod, your migrations history diverges. The runbook in core/.claude/rules/database.md covers recovery.
