firebase

Firebase as the backend: Auth + Firestore + Storage (+ optionally Cloud Functions). The integration adds rules for security, query patterns, and rule-file discipline.

databaseauthstorageBaaS

Apply command

bash scripts/apply.sh --base=react-vite-ts --integrations=firebase ../my-app
# or use the preset:

Environment variables

# Firebase Web SDK (browser-safe — these are public)
VITE_FIREBASE_API_KEY=...
VITE_FIREBASE_AUTH_DOMAIN=...
VITE_FIREBASE_PROJECT_ID=...
VITE_FIREBASE_STORAGE_BUCKET=...
VITE_FIREBASE_MESSAGING_SENDER_ID=...
VITE_FIREBASE_APP_ID=...

# For Next.js, use NEXT_PUBLIC_FIREBASE_* prefixes instead.

# Admin SDK (server-only — never expose):
FIREBASE_SERVICE_ACCOUNT_JSON=...  # the entire service-account JSON, base64-encoded
The Web SDK config is not secret — Google designed it to be safe in client code. Security comes from firestore.rules. That said, lock down the API key in the Firebase console (HTTP referrer restrictions) for hygiene.

Rule file highlights (firebase.md)

  • Security rules are not optional. The default allow read, write: if false; stays until you write a real rule. "It works because rules are open in dev" is a bug.
  • Test rules with the emulator. Use firebase emulators:start --only firestore and run rule tests against it.
  • Listeners must clean up. Every onSnapshot in React needs a corresponding unsubscribe in the cleanup return.
  • Don't query without limits. limit(N) on every Firestore query unless you've explicitly designed the collection size.
  • Auth state in Server Components needs the Admin SDK + a token-verification step. The Web SDK is browser-only.
  • Storage rules live in storage.rules, separate from Firestore.

Combined with other integrations

  • + tailwind on a frontend base — see the firebase-react preset.
  • + supabase — unusual but technically valid. Pick one for primary data; use the other for a specific concern (e.g. Firebase Auth + Supabase Postgres). The code-review hook will flag duplicated auth flows.

Gotchas

  • Bundle size on Next.js. The Web SDK is large. Import only the modules you need (firebase/auth, firebase/firestore) — never the full firebase entrypoint.
  • Admin SDK in serverless functions. Initialize once outside the handler — cold starts will pay the price otherwise.
  • Service account JSON. Store it base64-encoded in env, not as a multi-line value. Many platforms don't handle multi-line env vars well.
  • The Firebase Auth user object is mutable. Always re-fetch fresh tokens (getIdToken(true)) before sending to your server.

Smoke test after apply

cd ../my-app
npm install firebase
# Fill .env.local with the Web SDK config, then:
cat > src/lib/firebase.ts << 'EOF'
import { initializeApp } from "firebase/app";
export const app = initializeApp({
  apiKey: import.meta.env.VITE_FIREBASE_API_KEY,
  authDomain: import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
  projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
});
EOF
npm run validate
