Default SDLC workflow

This is the default workflow that ships with the boilerplate. /start <task> runs the classifier, the orchestrator routes to the matching pipeline (nano / standard / full), and the agents hand off stage by stage until the change is merged.

This is the default — your team can add more. Drop additional workflow files in .claude/workflows/project/ (anything under project/ is user-namespaced — the boilerplate's upgrade machinery never touches it). See How to add your own workflow at the bottom of this page.

Three tiers — the classifier picks one

The classifier (~50 tokens) runs first on every /start. It emits <task_size>nano | standard | full</task_size>. The orchestrator loads the matching pipeline.

TierWhen it fitsPipelineCost
nano 1–2 files · obvious fix · no contract or schema change · no new deps Build → Review ~400 tokens
standard 2–5 files · contained to one layer · clear scope CEO (lean) → Build → Review → Ship (lean) ~1500 tokens
full New service · cross-cutting · security-sensitive · >5 files CEO → Eng → [Design] → Build → Testing → Review → Ship 4000+ tokens

Five flow types — picked by CEO

After the classifier picks the tier, the CEO emits a <flow_type> tag that determines which agents are skipped. From .claude/workflows/orchestrator.md:

flow_typeStage sequenceUse case
backend-featureCEO → Eng → Build → Testing → Review → ShipAPI endpoints, services, middleware (no UI)
frontend-featureCEO → Eng → Design → Build → Testing → Review → ShipAnything that touches the UI
hotfixCEO → Build → Testing → Review → ShipProd emergency. Skips Eng (no spec doc) and Design.
design-onlyCEO → Design → Review → ShipDesign tokens, UI kit changes, no code
security-patchCEO → Eng → Build → Testing → Review → ShipTesting stage adds security-guidance plugin

Loopback rules

When a downstream stage fails, the orchestrator returns to a specific upstream stage with structured findings. Maximum 3 cycles per stage pair; on the 4th cycle, escalates to CEO for scope reassessment.

FromConditionReturns toContext passed
TestingAny test failsBuildFailure log from docs/progress.md
Testingsecurity-guidance flags partial fixBuildsecurity-guidance plugin output
ReviewAny BLOCKER findingBuildFull review checklist
ReviewSpec compliance failureEngSpecific compliance gaps

How to add a custom workflow

The default workflow above covers most teams. If yours has a different shape — say a stricter compliance gate, an extra security review, or a different stage order — you don't fork the boilerplate. You drop a new workflow into .claude/workflows/project/ and it lives alongside the defaults.

1. Where it lives

Path: .claude/workflows/project/<workflow-name>.md

Anything under .claude/workflows/project/ is user-namespaced — the boilerplate's apply.sh upgrade never overwrites or removes it. The defaults stay in .claude/workflows/{orchestrator,pipeline-nano,pipeline-standard}.md.

2. Minimal structure

# <Workflow name>

## Trigger
<When does the orchestrator load this workflow? Usually via flow_type tag from CEO.>

## Stage sequence

CEO → Eng → Build → Testing → Review → Ship

(or whichever stages fit your process)

## Gates
| Stage | Gate condition | Hard block? |
|---|---|---|
| ... | ... | Yes/No |

## Loopbacks
| From | Condition | Returns to | Context |
|---|---|---|---|

## Plugins used
- <plugin-name> — <which stages call it>

## Branch naming
<If different from the default feature/bugfix/hotfix scheme>

3. Wire it into the orchestrator

The CEO agent emits a <flow_type> tag based on the task. The orchestrator (.claude/workflows/orchestrator.md) reads that tag and loads the matching workflow file. To add a custom flow:

  1. Pick a flow_type identifier — e.g. compliance-audit, data-migration, vendor-integration.
  2. Override the CEO agent by adding .claude/agents/ceo.override.md teaching it when to emit your new flow_type (e.g. "if the task mentions PII, GDPR, or SOC2, emit <flow_type>compliance-audit</flow_type>"). The override file is read alongside the default; conflicting guidance defers to the override.
  3. Tell the orchestrator about it by adding .claude/workflows/orchestrator.override.md with the routing rule for your new flow_type. Same override-file convention.

4. Verify it

bash scripts/check-setup.sh
# Verifies the new workflow file exists and is non-empty.

/start <a task that should trigger your workflow>
# The classifier and orchestrator should route to your custom flow.
# If CEO emits the wrong flow_type, refine the override.

5. Examples teams have built

For inspiration — these aren't shipped, but they're the kind of customisation that fits naturally:

  • compliance-audit — CEO → Eng → Build → Testing → Compliance → Review → Ship. Adds a Compliance stage between Testing and Review that runs a custom checklist agent.
  • data-migration — CEO → Eng → Build → Dry-run → Testing → Review → Ship. Adds a dry-run stage that executes the migration against a snapshot.
  • vendor-integration — CEO → Eng → Build → Testing → Contract-verify → Review → Ship. Adds a stage that hits the vendor's sandbox API and verifies the response contract.
